# 公开痕迹检索：能做到哪一步

> 2026-11-16。配套代码：`maigret/cn/content.py`（页面解析）、
> `maigret/cn/footprint.py`（检索）、`maigret/cn/data/forums_cn.json`（站点清单）。
> 合规判断的依据见 [`content-access-feasibility.md`](content-access-feasibility.md)。

## 1. 一句话定位

**检索层只负责"把能公开读到的原始材料取回来"，推断留给报告之后的 AI。**

这不是偷懒，是分工。反过来做（工具直接输出"你多大、在哪上学"）有三个问题：
推断会过时、会出错、要负责任。而原始材料（某年某月某日某人说过某句话）
不会过时，也可以被核对。分开之后，材料能一直积累，推断随时能重做。

---

## 2. 人肉搜索的过程 vs 本工具能做到的

被检索的过程通常是这样，逐条对照本工具：

| 人肉搜索的一步 | 本工具 | 说明 |
|---|---|---|
| 1. 拿用户名到各平台搜账号 | ✅ 已有 | 就是现有的站点判定 |
| 2. 打开每个账号主页看资料 | ✅ 增强 | + 公开接口（GitHub 注册/动态时间）、Discuz 空间页（注册/最后访问/最后发帖/在线时长/**回帖数/积分**） |
| 3. 看这个账号列出的内容 | ✅ 新增 | 博客/文档站的文章列表（标题+日期）、GitHub 的仓库与动态 |
| 4. 翻这个人的发帖、回帖 | ⚠️ 仅限已知帖子 | **资料页签名里的帖子会自动跟进**；但"列出他发过哪些帖"做不到（见 §6） |
| 5. 从帖子里看他在哪个吧/版块 | ✅ 已有 | 版块名本身就是强线索（"某某中学吧"） |
| 6. 抽地名、学校、单位、联系方式 | ✅ 部分 | 只抽原文里的字面值，不做判断（见 §5） |
| 7. 拿线索再去搜，循环 | ⚠️ 人工 | 不给工具自动循环（那是爬虫），线索列出来给人 |
| 8. 汇总时间线推年龄、学段 | ❌ 不做 | 交给 AI 分析（见 §1） |

第 4 步在 2026-11-16 有一次重要补充：**资料页"个人签名"里的帖子地址会被自动跟进**。
这条路径之前漏了，导致 Web 端跑论坛那一路只拿到资料页那一行元信息——
用户看到的正是"有同名账号，但没提取到什么有效信息"。

签名是唯一不需要人肉找、也不需要绕过服务端限制的"发现"路径，
因为**地址是用户自己写在公开资料上的**。实测 `yang11235` 的签名里就有
`thread-481192-1-1.html`。

第 4 步的差异要说清楚：**本工具能"深挖一个已知的帖子"，不能"发现帖子"。**
发现那一步在原来的方案里打算用搜索引擎，但实测**四个引擎的 robots 全部禁止
结果页**（360 `Disallow: /s`、百度与搜狗 `Disallow: /`、Bing `Disallow: /search`），
且 360 约 40 次请求就封 IP 十几分钟。所以这一步交回给人——他自己用浏览器搜，
把找到的帖子地址用 `--cn-thread` 喂进来。

第 3 步是这一轮补上的：主页上列出的内容不需要"发现"，账号存在就有地址。
这一块能明显改变产出——从"只有 1 条论坛注册时间"变成"25 条跨 17 年的时间线"。

这看着像"少做了"，其实是把这个工具唯一可能变成人肉搜索器的地方堵死了：
**能自动发现全网痕迹的工具，就已经不是自查工具了。**

## 3. 具体能拿到什么（实测）

### 3.1 默认运行（不带任何额外参数）

```
$ python -m maigret yang11235 --cn-footprint

公开痕迹检索：yang11235
────────────────────────────────────────
  共 25 条痕迹，时间跨度 2009-01-12 ～ 2026-11-16

  GitHub                   24 条
  bbs.newwise.com           1 条
```

`GitHub` 那 24 条来自公开接口（账号 + 仓库 + 动态），
`bbs.newwise.com` 那条是论坛资料页的注册/最后访问/最后发帖时间。

### 3.2 再喂一个帖子地址（`--cn-thread`）

同一个用户名，加一条种子地址后，论坛那一路从 1 条变成 17 条
（该用户在这个帖子里的全部发言，带精确时间）：

```
共 17 条痕迹（论坛部分）

  出现过的版块/吧
    · [卡牌列表]

  时间线
    2009-09-18  妈妈啊…根本就没有强化仪式嘛…终焉先生，你是不是走错房间了…
    2009-09-18  现在终焉你炸给我看我只是客人 发表于 2009-9-18 12:28 有什么问题么…
    2009-09-20  自然受可以接受。。。老希去死。。。。为什么攻那么高。。那么容易出。。。
    2009-10-29  感觉SR都还不错啊~无欲应该是NR吧。。。。
    2009-11-11  杯具啊。。。太阳神官居然SR。。还想撩来着。。。
    ...
```

从这份材料里能读出的事实（工具不写，AI 来写）：

- `注册时间 2009-01` 与 `最后访问 2012-01` 划出论坛活跃期
- 活跃期内的发言集中在卡牌/游戏类版块
- 在线 1010 小时 / 回帖 1564，说明那几年投入很重
- GitHub 注册在 2024 年，2026 年的动态集中在阅读类工具

**这些都是原文，没有一处是推测。**"所以他 2009 年在读中学"这种话，
必须由报告之后的 AI 依据这些材料写，而且要标成推断。

## 4. 三个数据源，按可靠性排序

| 源 | 拿到的 | 为什么排这个位置 |
|---|---|---|
| **公开接口**（`apis.py`） | GitHub 账号注册时间、仓库创建/推送时间、公开动态（精确到分钟） | 字段稳定、时间带时区，不受前端改版影响。**能走接口就不解析页面** |
| **Archiver 精简页**（`content.parse_discuz_archiver`） | 指定帖子里的全部发言 + 精确时间 | 服务端渲染、无 JS，**同样内容只有正常页的 1/15 体积**（5.2KB vs 78KB） |
| **已知账号主页**（`content.py`） | 博客/文档站上列出的文章（标题+日期+链接） | 不需要额外"发现"——扫描已经给出账号，主页地址就有了 |
| **论坛资料页** | Discuz 的注册/最后访问/最后发帖时间、回帖数、签名里的帖子线索 | 需要先有站点清单 |

三者的共同点是：**都不需要"发现全网痕迹"这个能力**。这也是它们能存在的原因。

### Archiver 这条路径值得单独说

Discuz 自带一个给搜索引擎和老浏览器用的 `archiver/` 子站。实测它比论坛正常页强得多：

```
普通作者视图  forum.php?mod=viewthread&tid=436216&authorid=463889  78 KB
Archiver 视图 archiver/?tid-436216.html&authorid=463889          5.2 KB
```

**两者返回同样的 16 条发言与精确时间戳。** Archiver 小 15 倍，无 JS、无重排、不受皮肤影响。

另一个好处在合规上：`archiver/` **不在** robots 的 Disallow 列表里，而论坛自己的搜索页明确是 `Disallow: /search.php`。

所以现在优先走 Archiver，拿不到才退回普通页。这一改动让「深挖一个帖子」的请求数从 7 次降到 2 次。

接口层为什么排第一，举个实测对照：Gitee 的个人主页在静态 HTML 里
贡献日历是 0 条（数据靠前端拉），而 GitHub 的公开接口直接返回带时区的
时间戳。同样是"主页上的内容"，一个能拿一个拿不到——**能走接口就别解析页面**。

## 5. 为什么只抽"字面值"而不做判断

`content.mine_clues()` 只做两件事：

1. 按后缀锚点找地名/学校形态的串（`深圳中学`、`翠园中学`、`深圳市`）
2. 找邮箱、手机号、QQ 号（有明确格式）

**它不判断"翠园中学"是不是这个人的学校。** 理由：

- 帖子里出现的学校名可能是"我朋友在那个学校"、"那个学校食堂难吃"
- 中文没有词边界，硬抽必然出噪音（实测一开始把"我在深圳中学"整段当地名，
  已修正为剥掉开头的动词/代词）
- 判断错了的代价是用户照着一个错结论去改隐私设置——比漏报严重

## 6. 做不到的部分（重要，别指望）

| 做不到 | 原因 | 实测依据 |
|---|---|---|
| 列出某用户发过的所有主题 | Discuz 服务端禁用，**不是个别站的隐私设置** | 换活跃用户（uid 68956）与目标用户、换 `type=thread/reply`，全部返回「提示信息」 |
| 自动发现帖子 URL | 四个引擎的 robots 全部禁止结果页，论坛搜索页也被 robots 禁止 | 360 `Disallow: /s`、百度 `Disallow: /`、搜狗 `Disallow: /`、Bing `Disallow: /search`；论坛 `Disallow: /search.php` |
| 按作者筛 Archiver 版块页 | Archiver 版块页只有标题和回复数，**没有作者字段**，且固定 40 条不能翻页 | `archiver/?fid-8.html` 与 `fid-8-page-2.html` 返回完全相同内容 |
| 读权限版块里的帖子 | 版块级访问条件，游客永久不满足，**Archiver 也绕不过** | tid=481192 提示「访问条件：N币 ≥ 0 您的信息：N币: 0」，普通页与 archiver 页都被拦 |
| 贴吧的帖子正文（未登录） | 未登录一律 403 | 连续 12 次全是「百度安全验证」 |
| 知乎 / 微博 / 小红书 / 抖音 | robots 禁 + 需登录 + 签名 | 见 `content-access-feasibility.md` §5 |
| 从 JS 渲染的平台主页抽内容 | 页面里没有条目，数据靠前端接口拉 | Gitee 的贡献日历在静态页里 0 条 |
| 翻页翻到底 | 单帖最多 3 页、单站最多 3 个帖子、单次最多 60 次请求 | 刻意限制，见 §8 |

关于第一行要特别说清楚：**它不是"需要登录"，是 Discuz 关掉了这个功能。**
一开始我用 yang11235 测，得到「提示信息」，怀疑是隐私设置；换成一个
发过三万多积分、明显极度活跃的用户（uid 68956）再测，同样是「提示信息」，
`type=thread` 与 `type=reply` 都一样。确认是论坛级禁用。

关于第二行：Bing 的 robots 一开始只看开头几条，以为它只禁了
`/academic/search` 之类的子路径；把 2676 字节读完才发现 `*` 段里有
`Disallow: /search`。**读 robots 必须读完**，只读前几行会得出相反结论。

唯一的例外是贴吧：**用你自己的登录 Cookie 时帖子正文可读**（实测 1 秒间隔
连打 10 次无异常）。但这条没接进 `footprint.py`——因为风险落在用户自己的
账号上，那种事必须由用户明确知道并自己决定，不该是默认行为。

另外 `content.parse_tieba_posts()` 虽然写了，但**还没有用真实登录态页面验证过**
（手头没有可用的贴吧登录样本，class 名是从公开结构反推的）。用之前先
`--dump-response` 看一眼。它也不做"整页扫日期"的兜底——那样抽出来的条目
没有作者，会被当成"这个人说的话"记进去，把别人的话记到用户头上比少记严重。

## 7. 用法

```bash
# 默认用法：论坛资料页 + 已确认账号的公开接口/主页（不需要额外输入）
python -m maigret 用户名 --cn-footprint

# 指定论坛（默认用 cn/data/forums_cn.json 的实测清单）
python -m maigret 用户名 --cn-footprint --cn-forum bbs.newwise.com

# 喂一个你自己搜到的帖子地址，把他在该帖里的所有发言和时间抽出来
python -m maigret 用户名 --cn-footprint \
    --cn-thread "https://bbs.newwise.com/forum.php?mod=viewthread&tid=436216"

# 控制请求预算（默认 60）
python -m maigret 用户名 --cn-footprint --cn-footprint-budget 20
```

**默认关闭。** 它会对第三方站点发额外请求，不该在用户没要求时发生。

### Web 端

结果页的个人资料卡片下方有一个「检索公开痕迹」按钮，点它调
`POST /api/footprint/<job_id>`，返回 `summary` / `text` / `ai_material` 三份：
`summary` 给程序用（前端据此渲染表格），`text` 给人看，`ai_material` 给分析用。

**它刻意是按钮而不是自动跑。** 补检（`cn_probe`）是自动的，因为它只打几个
接口；痕迹检索会去第三方站点翻页，请求量是它的十倍以上。
两个按钮存在理由相反，不能混。

请求预算在接口里再夹一次（1..200）：前端传 `100000` 进来，等于让用户在
不知情的情况下对着别人服务器打一万次。

拿到 `summary` 之后，把 `to_ai_material()` 的输出交给 AI 分析：

```python
from maigret.cn.footprint import search_footprints, to_ai_material

summary = await search_footprints("用户名", session, seed_urls=[...])
material = to_ai_material(summary)   # 保留原话，不做摘要
```

`to_ai_material()` 与 `render()` 的区别是刻意的：
`render()` 给人看（挑重点、要短），`to_ai_material()` 给 AI 看
（保留细节和原话，因为它要靠"放学回来""翠园"这种字面信息去推）。

## 8. 内置的约束（不是建议，是硬限制）

| 约束 | 默认值 | 为什么 |
|---|---|---|
| 单次运行请求上限 | 60 | 没有上限的检索器，配上"页面里有链接就跟着走"的写法，自己就成了爬虫 |
| 同域名请求间隔 | 1.2 秒 | Discuz 站多是个人/小团队维护，打太快是真的会影响别人 |
| 单帖翻页上限 | 3 页 | "只看作者"视图实测不分页，普通视图 3 页已覆盖绝大多数人的发言 |
| 默认关闭 | 是 | 对第三方发请求这件事，必须由用户主动要求 |
| Web 端预算上限 | 200 | 前端传 `100000` 进来，等于让用户在不知情下对着别人服务器打一万次 |

预算与间隔是**在锁里原子扣减**的，并发下也成立——见 §8 末段。

另外有两条写死在代码里的判断：

**被拦就记"被拦"。** 403/验证页一律记成 `blocked`，绝不退化成"没查到"。
把"我没读到"说成"他没有"，是这个项目最不能犯的错。

具体到实现，这条要求三处都做到（缺一处就等于没做）：

1. `fetch` 把 403/验证页映射成 `blocked`；
2. Discuz 的**权限墙**（HTTP 200，文案是「您没有权限访问该页面」）也要认出来——
   Discuz 的「提示信息」模板同时用于"没有这个用户"和"没有权限"，
   **不能拿「提示信息」当"不存在"的判据**，只有「您指定的用户空间不存在」
   这类明确文案才算；
3. 种子里采集到的失败提示必须真的渲染出来（`render()` 与 `to_ai_material()`
   都读 `notes`），否则采集了也不显示，等于没采集。

**重复楼层按 pid 去重。** 实测 Discuz 的"只看作者"视图不响应 `page` 参数
（连打 page=1/2/3 返回相同 pid 集合），不检测重复就会拿到 3 份一样的内容。

**并发下预算与间隔真实生效。** 「查预算 → 等间隔 → 记账」三步必须在同一个锁里
做完：中间夹一个 `await`，并发任务就会读到同一份旧状态然后一起通过检查。
实测原写法在"预算 2、同域 5 并发"下发出了 5 个请求，其中 4 个在同一毫秒。
现在改为「原子预留额度」：预约不到就 sleep 后重试，而不是 sleep 完直接发。

**解析结果三态。** `parse_thread()` 与 `parse_entries()` 的返回值必须区分：

| 返回 | 含义 |
|---|---|
| `None` | 不是网页 / 所有解析器都不认识这个结构（解析规则没覆盖） |
| `[]` | 结构认识，但页面上确实没有内容（例如"没有权限"页） |
| `[...]` | 抽到了 |

把 `None` 折叠成 `[]` 的后果是"解析规则没覆盖"被显示成"这个人没发过言"，
而且没有任何地方会提示异常。

`parse_entries()` 还要多分一层：很多平台主页（GitHub、MyAnimeList、Twitch）
**本来就不列内容条目**，只显示资料与统计。这种情形报成"结构不认识"，
用户会以为工具坏了——所以措辞必须是"这页没有列出的内容条目"。

**接口采集的请求要计进预算。** 一个采集器内部打 2-3 个地址，
只按"调用一次"记一笔的话，多出来的请求是看不见的
（日志里只出现一次调用）。所以走 `reserve_slots()` 预留。

**已知主扫描结果里被接口覆盖的站点，不再抓 HTML。** 省一次请求，
也避免"主页结构不认识"这种误导性提示。

**Web 端的账号列表字段与 CLI 不同，不能照抄。** CLI 用 `results`，
Web 端 `build_reports()` 返回的是渲染用结构，**没有 `results` 这个键**——
主页地址要从 `individual_reports[*].claimed_profiles` 里取（见
`web/app.py: claimed_pages_from_report`）。按 CLI 的字段写会取到空列表，
症状是"痕迹检索一条都没有、也不报错"，很难从输出看出问题。

## 9. 站点清单怎么扩

`maigret/cn/data/forums_cn.json`，每条必须带 `verified_at`：

```json
"bbs.newwise.com": {
  "label": "壬天堂世界（游戏/卡牌）",
  "verified_at": "2026-11-16",
  "note": "实测记下的坑"
}
```

**没有 `verified_at` 的条目不会被加载**，读不到文件时退回内置清单。
两种处理都是为了同一件事：不能让"没验证过"或"读取失败"被显示成"没有痕迹"。

收录标准三条：匿名可读、是 Discuz 且能区分两种响应、robots 未禁止。

实际存活率很低，这一轮抽了两批共 **60 多个**候选中文论坛域名：

```
第一批 20 个 → 3 个既活又是真 Discuz
第二批 43 个 → 1 个（bbs.a9vg.com）
其余：域名解析失败 21、404 / 非 Discuz 结构 27、403/567/502 各 1-2
```

所以清单里只有 4 条，**不是没去找，是这批站真的关了很多**。
文件里另有 `_rejected` 段，记下试过但不能用的，免得下一个人重复试。
