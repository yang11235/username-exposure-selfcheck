# 内容层可行性：难度、合规与风控

> 2026-11-16 实测，接 `docs/retrieval-analysis.md`。
> 问题：如果不止看"主页存不存在"，还去访问**内容**（帖子、问答、回帖正文），
> 在尽量不违法、不被风控的前提下，难度有多大？
>
> 结论先行，分三句：
> 1. **技术上不难**，抽取结构都是现成的，一天能写出能跑的。
> 2. **合规上，主力路径全部不成立**——百度和 360 的 robots 明确禁止抓结果页。
> 3. **风控上，SERP 抓取是自杀式方案**：一个 IP 约 40 次请求就被封，封了
>    十几分钟以上没恢复。这不是"要注意频率"，是"这条路根本走不长"。

---

## 1. 先把三条路分开，它们的难度完全不同

| 路径 | 拿到的信息 | 技术难度 | 合规 | 风控 |
|---|---|---|---|---|
| A. SERP 摘要（不进阶） | 标题、摘要、日期 | 低 | **不可行**（见 §2） | **几十分钟封 IP**（见 §3） |
| B. 抓目标站内容页 | 帖子正文、楼层时间、互动 | 低 | 灰色，取决于站 | **贴吧必须登录**（见 §4） |
| C. 站内 API | 结构化发帖列表 | 中 | 灰色 | 大多需要登录/签名 |

上一份文档推荐的 P1 是 A。**本轮实测把这个推荐否掉了。**

---

## 2. 合规：主力 SERP 路径明确不可行

这一条是最硬的结论，与技术水平无关。

### 2.1 360 的 robots 直接禁掉搜索结果页

`https://www.so.com/robots.txt` 全文只有 58 字节：

```
User-agent: *
Disallow: /s
Disallow: /link
Disallow: /brw
```

`/s` 就是搜索结果页。**整个 SERP 抓取方案在 360 上是被 robots 明确禁止的。**
`/link` 是跳转链接，也禁了。

### 2.2 百度更彻底：通配段 `Disallow: /`

`https://www.baidu.com/robots.txt` 有 16 个具名 bot 段（每条都是
`Disallow: /s?` 等），最后一段：

```
User-agent: *
Disallow: /
```

`m.baidu.com` 同样，`*` 段里有 `Disallow: /s`。

**这意味着：对任何非具名爬虫（包括本工具），百度禁止访问整站。**
不只是结果页——是整个站。而 `tieba.baidu.com` 的 robots 里连 `*` 段都没有，
只列了 16 个具名搜索引擎 bot（Baiduspider / Googlebot / bingbot / Sogou / 
Sosospider / ToutiaoSpider 等），其中 `ToutiaoSpider` 是 `Disallow: /`，
其余都是 `Disallow: /club/ /f/shipin /f/search`。

严格按 RFC 9309 解释：`tieba.baidu.com` 没有 `*` 段 → 非具名爬虫**不受任何限制**；
但 `www.baidu.com` / `m.baidu.com` 有 `*` 段 `Disallow: /` → **全站禁止**。

这个差异很诡异，但它就是文本事实，不能靠"我觉得他本意是"去改写。

### 2.3 搜狗 `Disallow: /`

`www.sogou.com/robots.txt` 的 `*` 段就是 `Disallow: /`，1 万字节的规则
本质是"除具名搜索引擎外全部禁止"。

### 2.4 结论

```
360   禁止 /s            → SERP 路径不可用
百度  禁止 / 和 /s       → SERP 路径不可用
搜狗  禁止 /             → SERP 路径不可用
Bing  禁止 /search       → SERP 路径不可用（见下方更正）
```

**四个主力引擎全部明确禁止抓结果页。** 这条路彻底关闭，没有"剩下一个能用"。

> **2026-11-16 晚更正：** 本节原来写的是「Bing 仅禁部分子路径，技术上允许，
> 但内容不相关」。那个判断是**错的**，错在读 robots 的方法上。
> `cn.bing.com/robots.txt` 的 `*` 段共 101 行，`Disallow: /search` 在第 54 行；
> 当时只看了开头那几条（`/academic/search`、`/bfp/search`），下面那些同类的
> `/search` 没读到，就得出了相反结论。**读 robots 必须读完**，这条教训
> `docs/footprint.md` 里已经记过一次（Bing），这里是同一个错的第二次。
>
> 顺带修正另一个判断：`docs/footprint.md` 的"能不能做"表里把
> 「百度知道」列为"可做，注意编码"。按 RFC 9309 精确判定，
> `zhidao.baidu.com` 的 `*` 段是 `Disallow: /` —— 和主站一样全站禁止。
> 它"技术上能读 200/221KB"是真的，但合规上不可做。

所以"用 SERP 摘要做公开足迹"这条路，**合规上走不通**，不是频率问题、
不是加 User-Agent 问题、不是加延时问题。上一份文档把它列为 P1 是错的，
本轮更正。

### 2.5 商业 API 是唯一合规的 SERP 入口，但成本与覆盖都不合适

| 方案 | 状态（2026-11 核实） | 价格 | 中文覆盖 |
|---|---|---|---|
| Bing Search API | **2025-08-11 已退役**，不再发新 key | — | — |
| Google Custom Search JSON API | 已停止新用户，存量用到 **2027-01-01** | $5/1k，100 次/天免费 | 差 |
| Brave Search API | 可用，独立索引 300 亿页 | $3-5/1k，**2,000 次/月免费** | **差**（独立索引，中文长尾论坛基本没有） |
| SerpApi / SearchApi 等 SERP 抓取商 | 可用 | $4-25/1k | 好（就是转售百度/360 结果） |
| Grounding with Bing | 可用，仅在 Azure 内 | $14/1k | 差 |

两个关键判断：

- **Brave 这类独立索引对中文长尾没有用。** 我们要找的 `bbs.newwise.com`
  这种 Discuz 论坛，Brave 的索引里大概率没有。实测无法验证（本机代理不通），
  但从"300 亿页 vs 百度千亿级中文页"的量级差可以推断。
- **SerpApi 这类本质是转售被抓的百度/360 结果**，我们用它并不比自己抓更"合规"，
  只是把风险转移给了服务商。而且 Google 已于 2025-12-19 对 SerpApi 提起 DMCA 诉讼。

对一个**本地自用、一次查一个用户名**的工具，$5/1k 的成本可以忽略（一次检索
约 20 次查询 = $0.1），但中文覆盖不足是硬伤。

## 3. 风控：SERP 抓取的实际寿命是「约 40 次请求」

这组数字是今天实测的，值得单独记：

```
12:05  开始：360 桌面版正常，pn=1..5 全可用
12:12  约 40 次请求后 → 200 / 6466B / <title>访问异常页面</title>
12:14  移动版 m.so.com 仍可用（8 次后同样被封）
12:24  桌面版 + 移动版同时仍是「访问异常页面」（封禁持续 12 分钟以上）
```

关键点：

1. **封的是 IP，不是 session。** 换 UA、换 session、换移动版域名都没用；
   移动版被封后桌面版也一起是封的。
2. **至少 12 分钟未恢复**（12:12 封 → 12:24 仍在封，中途每 30-180 秒复查一次）。
   对自用工具来说，"用 40 次就得歇十几分钟"已经等于不可用。
3. **返回 200，不是 429。** 按状态码判"成功"，解析出 0 条结果，
   然后报告"这个用户名没有公开足迹"——**这就是把"我被封了"说成"你没暴露"**，
   是这类工具最不能犯的错。`cn/verdict.py` 里"先判被打断，再判存在性"
    这条原则，在 SERP 层同样适用。

对比一下量级：一次完整自查需要多少 SERP 请求？

```
查询矩阵：精确匹配 1 + site: 白名单 10 + 共现词 3  = 14 条
每条翻 2 页                                        = 28 次
能查几个用户名？          →  1 个（第一个就跑掉 70% 配额）
一天能查几次？            →  1-2 次
```

**这是"个人自查"勉强够用、"任何批量"完全不可能的量级。**
反过来说，这恰好与项目立场一致（README：「不做查他人的便利性设计。
无批量、无目标列表导入、无任务队列」）——如果真要做这一层，
这个物理限制反而是最好的护栏。

## 4. 抓目标站内容页：技术上最容易，但贴吧需要登录

### 4.1 贴吧帖子页：未登录 100% 拦截，登录后顺畅

同一个 URL，只差一个 Cookie：

```
未登录  https://tieba.baidu.com/mo/q/m?kz=535633213
        → 403 / 2463B / <title>百度安全验证</title>
        （连续 12 次，全部 403）

带 cookies.txt（含 BDUSS + TIEBAUID）
        → 200 / 115886B / <title>雷顿教授与最后的时间旅行剧情解惑！</title>
        → 连续 6 个不同帖全部 200，1 秒间隔连打 10 次无异常
```

抽出来的正文是完整的（手机版结构简单，反而好解析）：

```
雷顿教授与最后的时间旅行剧情解惑！
YANG11235   6   2009-2-6
RT
YANG11235   6   楼主  2009-2-6
2、为什么要把雷顿教授带来假十年后伦敦？答：两个原因，一克劳斯的游戏罢了，
二博士需要扫描雷顿的记忆。
```

**这里的难度不在技术，在"用谁的登录态"**：用自己的账号去批量读帖，
在平台看来就是"异常浏览行为"，风险落在用户自己的账号上。这是必须让用户
知情的一条——**不是工具的风险，是他账号的风险**。

### 4.2 Discuz 论坛：匿名可读，结构干净

`bbs.newwise.com`（Discuz! X5.0）匿名可读，抽取结构非常规整：

```python
# 一层楼一个 authi + 一个 authorposton
re.findall(r'<div class="authi">(.*?)</div>.*?<em id="authorposton\d+">(.*?)</em>', html, re.S)
```

实测 20 层楼全部抽出：

```
XYZ龙加农     发表于 2009-7-22 23:43:39
myq123        发表于 2009-7-22 23:44:54
marco833      发表于 2009-7-22 23:46:20
```

正文在 `<td class="t_f">` 里，连"本帖最后由 X 于 Y 编辑"这种元信息都在。

它的 robots 是标准 Discuz 模板：`*` 段允许大部分路径，禁掉
`/search.php`、`/member.php`、`/api/`、`/data/` 等。**帖子页 `/thread-xxx` 不在禁止列表里**，
合规上站得住。而且 `home.php?mod=space&username=` 也不在禁止列表里。

**这是唯一一条"合规 + 匿名 + 结构干净"都成立的路径。**

### 4.3 顺带修正上一份文档的一个错误

上一份文档说「SERP 的日期可用于推断上学时间」。实测发现 SERP 日期和真实楼层日期
**对不上**：

```
SERP 说 2006-09-02   真实楼层 2009-2-6       差 3 年
SERP 说 2002-08-11   真实楼层 2008-11 ~ 2009-4  差 6 年
```

原因是 SERP 摘要里的日期语义不统一：有的是"发帖时间"，有的是"最后回复时间"，
有的是"百度收录时间"。**拿它推年龄会推出错误结论。**

这就是"必须进内容页"的真正理由——不是为了看得更多，是为了**看对**。
标题、摘要都是二手信息，日期语义由搜索引擎决定，不是由帖子决定。

## 5. 逐站难度评级

按"合规 × 风控 × 抽取"三个维度给结论：

| 类型 | 代表 | 匿名 | 登录 | 抽取 | 结论 |
|---|---|---|---|---|---|
| Discuz 论坛 | newwise、多数中文 BBS | ✅ | 不需要 | 极干净 | **可做**，优先 |
| phpwind 论坛 | 少量老站 | 待测 | — | 类似 Discuz | 可做，需实测 |
| 贴吧 | tieba | ❌ 403 | ✅ 必须 | 简单 | 可做，**但用用户登录态** |
| 百度知道 | zhidao | ✅ 200/221KB | 不需要 | GBK 编码坑 | **不做**——robots `*` 段 `Disallow: /`（2026-11-16 更正） |
| 知乎 | zhihu | ❌ | ✅ | 复杂 | robots `Disallow: /`，**不做** |

## 6. 法律边界：哪条线不能踩

三条，按确定性排序：

### 6.1 明确不能做的

1. **绕过技术措施。** 破解签名（`xhs_xs` 那类）、逆向 App 协议、破解验证码——
   这些在《网络安全法》第 27 条和《刑法》285 条下有明确风险。
   项目现有 `schema.py` 里 `signature: xhs_xs` 这类字段**不该被真去实现**。
2. **抓取需要登录才能看的内容，且账号不是你自己的。** 用别人的 Cookie 抓，
   比用自己账号抓严重得多。
3. **对"未公开"内容下手。** 私信、仅好友可见、需要申请加入的私密组。

### 6.2 灰但可控的

4. **用自己账号读公开帖子。** 内容对游客公开，只是平台要求登录才能看。
   法律上争议不大，风险主要是**账号被封**，且这个风险由用户承担。
   必须在界面上说清楚，不能藏在文档里。
5. **robots 禁止但内容公开。** 严格说 robots 不是法律，是行业惯例。
   但对 360/百度这种明确 `Disallow` 的，**不做**——理由不是怕被告，
   是"被抓一次封 IP 半小时"已经让方案没有实用价值，合规只是顺带成立。

### 6.3 必须保留的产品约束

项目 README 现有的三条，在加了内容层之后更不能松：

- 无批量、无目标列表导入、无任务队列
- 不给处置建议
- 盲区必须显式出现

内容层比"注册存在性"敏感一个量级——前者是"你在哪些站有账号"，
后者是"你在 2009 年 8 月 13 日晚上 8 点说了什么"。**技术上一旦能批量，
这东西就变成了人肉搜索工具。** 现在这个形态（本地跑、一次一个、
用户自己看自己的）是它还是"自查工具"的唯一原因。

## 7. 如果要做，建议这么切

### 7.1 做

**只做「用户自己指定的那几个站」，不做全网 SERP。**

```
输入：用户名 + 用户自己粘贴的帖子 URL（或从 SERP 手工找到的 URL）
输出：这条帖子里提到该用户名的楼层 —— 作者、时间、正文
```

理由：把"发现 URL"这一步留给用户（他自己用搜索引擎搜，本来就会搜），
工具只做"把 URL 里的内容结构化"。这样：

- 不触碰 SERP 的 robots
- 不触发搜索风控
- 请求量 = 用户给几个 URL 就打几次，天然受限
- 合规上只访问"用户主动指定的公开页面"

### 7.2 不做

- 不做自动 SERP 抓取（robots 禁 + 封 IP）
- 不做全站遍历（`/f?kw=` 翻页、`search.php`）
- 不做批量用户名
- 不做需要破解签名的站

### 7.3 代码落点

新增 `maigret/cn/content.py`，与 `footprint.py` 分开：

```python
@dataclass
class Floor:
    author: str        # 楼层作者
    posted_at: str     # YYYY-MM-DD HH:MM:SS，抽不到留空
    text: str          # 正文
    floor: str         # 楼层号/楼主标记
    url: str           # 该楼层的锚点

def parse_discuz(html, username) -> list[Floor]
def parse_tieba_mobile(html, username) -> list[Floor]
```

两个解析器就够了——它们覆盖了绝大多数中文长尾。

复用现有的 `verdict.looks_like_captcha` / `looks_like_login_wall`：
**拿到 403 或验证页时返回"被拦"，绝不返回空列表。**
空列表的含义是"这帖里没有他"，被拦的含义是"没读到"，两者不能混。

## 8. 难度总评

| 维度 | 评价 |
|---|---|
| 技术实现 | **低**。两个正则解析器，各 50 行 |
| 合规风险 | **中**。Discuz 路径干净，贴吧路径灰色 |
| 风控风险 | **高**（SERP）/ **中**（内容页，取决于频率和登录态） |
| 维护成本 | **中**。Discuz 模板跨版本稳定，贴吧手机版随时可能改 |
| 对用户的真实风险 | **账号**。用自己登录态读帖，被封的是他自己 |

**给一个直接的回答**：如果你问的是"能不能做出来"——能，而且比想象的简单，
一天的工作量。如果你问的是"能不能做成一个自动去网上翻你足迹的东西"——
**不能，而且不该做**。合规上 SERP 全被 robots 禁掉，工程上 40 次请求就封 IP，
产品上它会把这个工具变成人肉搜索器。

可行的形态只有一个：**用户自己找到 URL，工具帮他结构化那几页内容。**
这个形态下，你原来问的"从发言时间推出上学时间和年龄"照样能做到——
只是"找到哪几页"这一步，交回给人。
