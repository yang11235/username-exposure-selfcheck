# 检索能力增强：从「只查注册过没」到「查说过什么」

> 2026-11-16 晚。接 [`retrieval-analysis.md`](retrieval-analysis.md) 与
> [`content-access-feasibility.md`](content-access-feasibility.md)。
>
> 前两份文档的结论是「SERP 这条路走不通」。那份结论今天又验证了一遍，
> 并且**又发现一处读错 robots 的地方**（见 §1.3）。
> 但"走不通"不等于"没得做"——本文记录的是**绕开 SERP 之后的四条路**，
> 每条都有真实产出。

---

## 1. 先把"弱"拆成四个具体原因

用户的原话是"检索情况很弱，还不如搜索引擎摘要"。这句话对应四个不同的问题，
把它们混在一起谈，就会得出"要抓搜索引擎"这个既不合规也做不到的结论。

### 1.1 原因一：判定层有一半结论不可信（假阳性）

`yang11235` 默认扫描 15 条命中，反例对照后真命中 6 条——**53% 是假阳性**。
根因是上游 1898 条「纯状态码」规则（200 就是命中），在前 520 站里占 43%。
中文站的典型失效形态恰好是「WAF 返回 200 + 验证页」，这类规则在那批站上
不是"偶尔不准"，是"每次都错"。

**这一层已有护栏**：`cn/scoring.py` 里 `statsonly` 走 `STATUS_ONLY_CONFIDENCE = 0.5`，
固定中低档、进不了高置信。所以它不会让用户"以为安全"或"以为暴露"，
只会让命中数虚高。**不改**（把弱规则摘掉会让命中数从 15 掉到 6，
用户第一反应是"功能变差"，正确的处理是报告里分开呈现）。

### 1.2 原因二：内容层几乎空白（这是真正的缺口）

这是"不如搜索引擎摘要"的**直接**原因。搜索引擎给你的每条结果都带
标题、摘要、日期；而本工具在 2026-11-16 之前的产出是：

```
GitHub        24 条   ← 唯一有内容层的平台
bbs.newwise    1 条   ← 只有一行"注册时间"
```

为什么只有 GitHub：`apis.py` 只写了 GitHub 一个采集器，
`content.parse_entries()` 对中文平台**全部返回 0 条**（实测 CSDN/Gitee/掘金/豆瓣
四个主页，三个 0 条、一个误抽）。也就是说工具"查到了账号"却"抽不出内容"。

### 1.3 原因三：SERP 这条路是真的关死了（不是没试够）

四个主力引擎的 `robots.txt` 按 RFC 9309 精确判定（最长匹配、最具体 UA 组）：

```
360   www.so.com        User-agent: * / Disallow: /s /link /brw     → 禁
百度  www.baidu.com     16 个具名段 + 末尾 * / Disallow: /          → 禁全站
搜狗  www.sogou.com     * 段 Disallow: /                            → 禁全站
Bing  cn.bing.com       101 行 * 段，第 54 行 Disallow: /search     → 禁
```

**Bing 这一条是本次新发现的更正。** `content-access-feasibility.md` §2.4
原来写"Bing 仅禁部分子路径，技术上允许"——那个判断错在读法上：
只看了 robots 开头那几条（`/academic/search`、`/bfp/search`），
没读到第 54 行的 `/search` 就下了结论。

同一个错在两份文档里出现过两次（`docs/footprint.md` 记过一次），
所以这次把纠正方法写死了：**`robots.txt` 必须整份读完再判**，
用 grep 判"有没有 /search"会漏掉具名段与 `*` 段的差异，用眼睛看开头会漏掉后面。

顺带更正：百度知道 `zhidao.baidu.com` 的 `*` 段是 `Disallow: /`，
§5 评级表里原来写"可做，注意编码"，现改为不做。

### 1.4 原因四：站内搜索返回的是分词噪音，不是结果

实测掘金搜索接口 `key_word=yang11235`：返回 **19 条**，
其中**逐字含该用户名的 0 条**。它把 `yang11235` 切成了 `yang` + `11235` 两个词，
命中的是"跨域""组件化"这类文章。

这解释了一个很容易误判的现象：**接口通了、条数不少、但全是无关内容**。
比"接口报错"危险得多，因为下游会把它当数据。

对照：网易云用户搜 `yang11235` 返回 3 条，其中**逐字相等 1 条**
（另两条是 `yang112357` / `yang112358`）。所以"站内搜索"这个方向本身是对的，
关键在**必须做逐字精确匹配**，且**不是每个平台的搜索接口都值得接**。

## 2. 绕开 SERP 之后，真正能补的四条路

按"信息密度 × 合规确定性"排序。四条的共同点是：**都不需要搜索引擎**。

### 2.1 GitHub `author:` 搜索 —— 补上"说过什么"

原来只取 `/users/{u}`（注册时间）、`/repos`（仓库）、`/events/public`（动态）。
这三样都只说"他有个账号、建过什么仓库"，**没有一个字是他自己写的**。

新增 `/search/issues?q=author:<u>`：返回**他自己提交的 issue 与 PR 标题**。
实测 `yang11235` 得到 7 条，全部带创建时间：

```
2026-09-17  [Feature] 书架/收藏夹支持多选书籍批量下载（finlater/weread.koplugin）
2026-10-17  feat(read_report): expose reporting interval presets（…/pull/210）
2026-11-14  fix(web): build each per-username report from its own results（soxoj/maigret）
```

区分 issue 与 PR（`pull_request` 键存在即为 PR）：两者反映的参与程度不同，
混成一个桶就看不出他在"提需求"还是"改代码"。

合规：`api.github.com/robots.txt` 是 404（未设限），匿名配额 10 次/小时
（core 60 次/小时），一次自查用 1 次。

### 2.2 网易云「歌单创建时间」—— 中文平台上最强的时间线信号

中文平台的主页地址基本不能用用户名拼出来（网易云是数字 uid、掘金是 24 位 id）。
但**站内搜索能把昵称换成 uid**，再用 uid 取内容列表。这条链不经过搜索引擎。

    /api/search/get/web?s=<昵称>&type=1002    → userprofiles[]（含 userId）
    /api/v1/user/detail/<uid>                 → 等级 / 听歌数 / 注册天数
    /api/user/playlist/?uid=<uid>             → 歌单列表，每个带 createTime

为什么歌单时间值得单独做成一条：它是**起点 + 持续活跃的证据**，
而且粒度到日。实测一个账号拿到 7 个歌单：

```
2013-06-18  我喜欢的音乐（232 首）   ← 平台注册时自动创建，等同注册时间
2016-09-25  德沃夏克（42 首）
2019-08-23  Humoresque, Op.101, No.7（1 首）
2020-04-24  俗人听的古典乐（17 首）
2021-04-09  开车时应该听的歌（8 首）
2025-08-11  小紫薇（52 首）
```

三道过滤，缺一条就会把别人的数据算到他头上：

1. **昵称逐字相等**（忽略大小写与首尾空白）。不做包含匹配——实测
   `yang11235` 搜出 `yang112357`（黑龙江）、`yang112358`（河北），
   不比对就会把这两个省的属地写进他的画像。
2. **歌单 `creator.userId` 必须等于目标 uid**。接口理论上只回本人的，
   但这个字段是可核对的事实，核对一次很便宜。
3. **`createTime` 必须合理**。实测老账号返回 `-1`，直接 `strftime` 会得到
   **1969-12-31**——报告里出现"1969 年创建的歌单"，用户会以为是真的。

合规：`music.163.com/robots.txt` 的 `*` 段对 `/api/search`、`/api/user/playlist`、
`/api/v1/user/detail` **全部允许**（逐个按 RFC 9309 判定过）。

不取的：听歌记录（`/api/user/record`，"在听什么"比"建过什么歌单"敏感得多）、
关注/粉丝列表（那是别人的数据）。

### 2.3 页面内嵌 JSON —— 一次修好一整类站

中文平台大量用 Vue/Nuxt/Next 做前端，**文章列表不在 HTML 里**，
而在 `window.__INITIAL_STATE__` 这种内嵌 JSON 里。

原有 `parse_entries()` 只有两条路：博客园专用解析 + "日期配附近链接"的通用兜底。
对这类页面两条都抽不到——页面上根本没有"日期+链接"的 HTML 形态。
于是"这站有 20 篇文章"被显示成"这页没有列内容"。

新增第三级 `_parse_embedded_json()`，认三种挂载点：

    window.__INITIAL_STATE__ = {...}          CSDN 等
    window.__NUXT__ = {...}                   Nuxt 站
    <script id="__NEXT_DATA__">{...}</script>  Next 站

实测效果（CSDN 博客主页）：通用配对 **0 条** → 内嵌 JSON **20 条**，
全部带 `postTime` 精确到日。

两个设计取舍：

- **只取"最长的那个列表"**，不合并。同一页里 `latelyList`（20 条文章）与
  `columnModule`（11 条专栏）并存，合并会把专栏也当文章发出去。
- **只认白名单键名**（`latelyList` / `articleList` / `postList` / ...），
  不做"遍历所有 list"——那会把 `tags`、`images`、`adList` 当成内容。

### 2.4 修掉通用配对的"把别人名字当标题"

实测豆瓣活动页，通用配对抽出一条：

```
2011-12-30  LEE-H
```

`LEE-H` 是**活动发起人**（别人），被记成了"他在 2011-12-30 发布的内容"。
把别人的名字记到他头上，比少记一条严重得多。

原因是只看链接文本判不出来——`LEE-H` 本身干干净净。必须**看链接前文**：
紧跟在「发起人：」这类标签后面的链接是元信息，不是内容。
已加 `_looks_like_title()`（排除 `标签：值` 形态、纯计数、只有日期）
与 `_META_LABEL_HEAD`（检查链接前 24 字符）。

## 5. 还能怎么补（按性价比排序，都未做）

1. **Discuz 站清单继续扩**。现在只有 4 条。按 `forums_cn.json` 的记录，
   抽测 60+ 个候选域名只有 4 个活着的真 Discuz——不是没找，是站真没了。
   这条路 ROI 已经很低。
2. **phpwind 解析器**。另一套中文论坛模板，与 Discuz 结构不同。
   没测过，不敢说难度相同。
3. **更多"昵称搜索能换 uid"的平台**。网易云验证了这条链路可行。
   可试：豆瓣（`/people/` 直接可读，但需要 uid）、快手、小红书（都要登录）。
   **判断标准只有一条：搜出来的结果能否逐字比对。**
   掘金就是反例（分词噪音）。
4. **把 `to_ai_material()` 的提示词专门写一版**。现在 `ai_prompt.txt` 是为
   "字段抽取"写的，不是为"从时间线推人生阶段"写的。材料已经够，
   缺的是让 AI 正确使用材料的指令。
5. **贴吧 + 用户自己的登录态**。技术上完全可行（实测带 BDUSS 后 200×6 篇），
   但风险落在**用户自己的账号**上，必须做成显式开关 + 界面明示。

## 6. 一句话总结

"检索弱"不是一个问题，是四个：假阳性多、内容层空、SERP 关死、站内搜索有噪音。

前两个能修，后两个修不了但能绕。**绕的办法只有一个方向：
不去问搜索引擎"网上有什么"，而是去问"这个平台自己公开了什么"。**
平台自己公开的东西（账号、仓库、议题、歌单、文章列表）既合规又准确，
而且带真实时间戳——这恰好是搜索引擎摘要最不可靠的地方
（SERP 日期与真实楼层日期实测差 3–6 年，见 `content-access-feasibility.md` §4.3）。

## 7. 第二轮扩展：把「一个站一个采集器」变成「一套协议一类站」

> 2026-11-16 晚补。第一轮之后收集面是 GitHub + 网易云 + Discuz 资料页，
> 本质是**逐站手写**——想多覆盖一个站就要多写一份解析。这一轮找到两个
> 「一次实现覆盖一整类」的入口，另外修掉一个会污染全部结论的归因 bug。

### 7.1 最重要的发现：Discourse 的 `topics/created-by`

Discourse 是当前技术社区最主流的论坛程序（openKylin、Appinn、openSUSE 中文、
Rancher、NVIDIA 中文论坛都是）。它把同一份 JSON 挂在每个页面的 `.json`
后缀上，不需要 API key、不需要登录：

    /u/<user>.json                     账号存在→200，不存在→404
    /topics/created-by/<user>.json     他创建过的主题列表（标题 + 时间）

**第二条补上的正是 Discuz 明确做不到的那件事。** `docs/footprint.md` 里记着：
Discuz 的"列出该用户发过的主题"（`do=thread`）被服务端关掉了，换活跃用户、
换 `type=thread/reply` 全都返回「提示信息」。所以此前"他参与过哪些帖子"
只能靠人工喂 URL。

而 Discourse 直接给这个列表。实测 `sam` 在两个站拿到：

```
2026-11-13  【训练营第二期结营作业】我做了通用安卓手机助手
2026-07-08  【学习工作赛道】FileCollector——AI 时代的上下文编排与收集工具
2026-03-06  （账号）信任等级：1；累计阅读秒：4023
```

实测 9 个站可用，字段带精确时间戳（`created_at` / `last_seen_at` /
`last_posted_at` / `time_read` / `trust_level`）。

### 7.2 合规上的一条新教训：**同一个站的不同路径，robots 立场可以相反**

Discourse 的默认 robots 里有 `Disallow: /u/`（担心用户页被爬爆）。
实测 9 个站里 4 个禁 `/u/`：

```
bbs.openkylin.top / discuss.jittor.cn / forums.rancher.cn / forum.robloxdev.cn
```

但 **`/topics/created-by/` 在 9 个站全部允许**。

所以实现上不能"这个站允许/不允许"一刀切，要**逐路径判断**：
禁 `/u/` 的站只取主题列表，不禁的两样都取。`DISCOURSE_SITES` 里那个
布尔值就是干这个的。

### 7.3 预算教训：接口层不能把额度吃光

第一版把 Discourse 封顶设成 18 次（9 站 × 2 路径）。结果是：预算 20 时
接口层一次预留就把额度占满，后面的论坛资料页、已确认账号主页、种子帖子
全拿不到配额——症状是"接口有数据，痕迹检索却一条论坛内容都没有"。

改成 6 次，并且**优先跑 robots 允许 `/u/` 的站**（一次能产出"注册时间 +
最后活跃 + 主题列表"），同样的请求数换更多信息。

另外 `_REQUESTS["collect_discourse"]` 改成引用 `DISCOURSE_REQUEST_CAP`
常量而不是写死数字——写死过一个 12，改常量后忘了同步，测试立刻红。

### 7.4 内置账号必须跳过

实测 `system` 在 7 个 Discourse 站命中、共 **90 条主题**，内容全是站务公告
（「提问前，请首先阅读」「2024 年度回顾」）。

如果用户搜的正好是 `system` / `admin`，输出会变成"这个人在 7 个技术论坛
都是管理员"——而那 7 个账号分属 7 个不同运营方，与他毫无关系。
已加 `DISCOURSE_RESERVED` 白名单（system / admin / moderator / discourse /
staff / support / team / guest / anonymous），命中直接不产出。

**产出为零好过产出一堆别人的站务公告。**

### 7.5 修掉两个会污染全部结论的归因 bug

这一轮最重要的修复，跟扩展无关，是测出来的。换 `neil` / `sam` 实跑时
发现两者的"联系方式"**完全相同**：`184822951@qq.com`、`13950133910`——
而这是不可能的。追下去挖出两个独立的 bug，它们串在一起造成了同一个后果：
**把别人的手机号和邮箱记到目标用户名头上。**

#### bug 1：`site_links` 扫了整页，不只是签名

`_extract_site_links()` 原来在 `html_text` 里也扫了一遍帖子链接，
理由是"有些人写在个人介绍里而不是签名"。

实测证明代价无法接受：`bbs.wuyou.net` 的资料页侧栏含公共区块
（"最新帖子""热门话题"），那些 tid 对**所有用户**都一样。于是
`neil` 和 `sam` 都拿到 `site_links=['403684']`，各自去拉同一个帖子的
全部楼层——两个不同的人拿到 93 条**完全相同**的内容，包括别人的
捐款回帖和联系方式。

修法：只认签名。签名是他自己的内容，整页 HTML 不是。
代价是写在"个人介绍"里的帖子链接会漏掉——**只会少查，不会错记**，
这个交换是划算的。

#### bug 2：Discuz 第四种字段形态没覆盖

`bbs.wuyou.net` 的资料字段是 `<li>注册时间: 2004-1-3 21:14</li>`，
**没有 `<em>` 包裹**。原有三种形态（`<em>` / `<dt><dd>` / `<a>标签 数字</a>`）
一个都匹配不上，于是真实账号（2004 年注册）被判成"没有这个人"。

这是**漏报**方向，和软 404 的误报方向相反，但同样要修：
用户会看到"这个论坛没有我"，而他 2004 年就注册了。

补上形态四：`<li>已知标签: 值</li>`。只认已知标签 + 冒号，
不认"任意 `xx: yy`"——后者会把时区、货币单位、好友列表全当资料字段。

#### 一个中途判断错的插曲（值得记）

第一轮修软 404 时，我把 `neil` 也判成了"不存在"，误以为是判据不够严。
实际相反：`neil` 在 wuyou 是**真实账号**，只是走到了 bug 2。
教训是——**同一个现象（"解析不出资料"）背后可能是方向相反的两种原因**：
"这个人不存在"和"这个人的页面结构我没覆盖"。先把两种可能都列出来再改判据，
否则会把漏报修成误报，或者把误报修成漏报。

### 7.6 跨站同名的显式提醒

一次跑 9 个论坛，很容易冒出一排"同名账号"。用户的第一反应是
"他到处都在"，而这些账号可能只是重名。

`summarize()` 现在会数一下：有 3 个以上站点命中「账号」类痕迹时，
在 `render()` 与 `to_ai_material()` 里都插入一句显式提醒：

```
关于同名的提醒
  · 3 个站点都有这个用户名（GitHub、Trae 社区、小众软件论坛）。
    **它们是否属于同一个人需要自行确认**——通用用户名在不同站点被不同人注册是常态。
```

必须进 AI 素材，否则 AI 会把"多个站有同名账号"直接写成
"这个人在 N 个平台活动"，而那是没有依据的推断。
